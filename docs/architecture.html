FNOL Intake Platform Architecture

An AI-assisted first notice of loss system for agents and policyholders. A cascade of Gemini and Claude models on Vertex AI listens to calls from Google Customer Engagement Suite, extracts and checks. A versioned rules engine makes sure every claim captures what Wisconsin, Illinois or Michigan law and the company's SOPs require before it reaches Guidewire ClaimCenter or the in-house claims system.

01Scope & design principles

The platform owns the intake window: from the first contact about a loss until a claim number exists in the core claims system and an adjuster is assigned. Coverage decisions, reserving and payment stay in the system of record.

Channels
  • Agent / CSR phone intake (primary)
  • Policyholder web & mobile self-service
  • Producer / broker portal
  • Email & document drop (ACORD 1/2/3 PDFs)
  • Partner API: TPAs, telematics crash alerts, body shops
Lines of business
  • Personal & commercial auto
  • Homeowners / commercial property
  • General liability
  • Workers' compensation (FROI)
  • Catastrophe mode for any line
Principles
  • AI suggests, a person confirms. No AI value is written without provenance.
  • Rules are data: versioned by state, line and effective date.
  • Cheapest model that can answer, escalate on low confidence.
  • PII is tokenized at the edge and never sent to a model in clear unless needed.
  • Every event is replayable and auditable.

03AI model cascade

Every intake event (a transcript turn, a typed field, an uploaded photo) enters the cascade at the cheapest tier. A tier answers only when its confidence clears that task's threshold. Otherwise it passes the event up with what it learned. Most events should never reach a large model.

Routing rules

  • Two providers per tier: every tier has a Gemini model and a Claude model behind one router interface. For each task, the model with the better score on the golden-transcript evaluation is primary and the other is the challenger. The challenger gets a small shadow share of traffic for comparison and takes over automatically if the primary times out or errors.
  • Per-task thresholds live in config (e.g. VIN slot 0.95, cause-of-loss 0.85, narrative summary 0.75) and are tuned from agent accept/reject rates.
  • Hard escalations skip tiers: any injury or fatality mention, a litigation or attorney mention, a catastrophe code, or a large-loss estimate goes straight to T2/T3.
  • Verifier: a second, cheaper pass checks T2/T3 output against the transcript (every extracted value must quote a source span) and against the JSON schema. Unsupported values are dropped.
  • Fallback: if a model endpoint fails or exceeds budget, the router returns the last good tier's answer and marks it unconfirmed. Intake never blocks on AI.
  • Cost guard: per-session token budget; semantic cache in Memorystore for repeated SOP questions.

04Agent intake copilot

The agent console has three panes: the live transcript, the claim form, and a Required Items checklist computed by the compliance engine. The copilot fills form fields from the conversation as suggestions; the agent accepts them with one key. The checklist reorders itself as facts arrive. Mentioning an injured passenger, for example, adds Medicare query fields and PIP questions.

Listens
  • Audio and transcripts from Google Customer Engagement Suite: Agent Assist streams live transcription and Conversational Insights keeps call analytics
  • Speech-to-Text streaming with speaker diarization and insurance phrase hints
  • Redaction of card numbers and SSNs in the transcript before storage
Prompts
  • Next best question, in plain language, ranked by what blocks submission
  • Mandatory disclosures as scripts the agent must mark as read: recording consent, state fraud warning, privacy notice
  • Empathy and safety cues: "Is anyone hurt? Are you somewhere safe?"
  • Translation help for non-English callers
Guards
  • Submit is disabled while any hard requirement is open
  • An agent may waive a soft requirement only with a reason code
  • Every field stores value, source, confidence and confirming user
  • Completeness score shown live and recorded for QA

05Compliance & SOP engine

Requirements come from three sources: state law and regulation, industry data standards (ACORD loss notices, IAIABC EDI for workers' comp, ISO ClaimSearch), and company SOPs. Each requirement is one record in a versioned ruleset, keyed by jurisdiction × line × coverage × effective date. The jurisdiction is the loss state for most lines and the jurisdiction state for workers' comp. The engine is deterministic. AI never decides whether a rule applies; it only supplies facts and explains rules to the agent.

Citations above are illustrative seed rules for design and test fixtures. Before production, each rule's text, deadline and applicability must be confirmed and owned by compliance counsel. Statutes and emergency orders change. The admin console requires a named approver for every ruleset version.

How rules are stored and run

  • Format: each rule has a condition in CEL (Common Expression Language) over the draft, a list of required field paths, a gate type, disclosure text by locale, an authority citation and an effective date range.
  • Lifecycle: draft → peer review → compliance approval → scheduled publish. Published versions are immutable in Postgres and cached in Cloud Run memory.
  • Pinning: a draft records the ruleset version it was evaluated against, so an auditor can replay any claim's checklist exactly.
  • RAG corpus: the same SOP and statute text is chunked into Vector Search so T2 can explain why a field is required, with a citation the agent can read.

Data handling rules

  • Classification: Public, Internal, Confidential (policy data), Restricted (SSN, MBI, driver's licence, medical, bank). Restricted values are tokenized by Sensitive Data Protection with a KMS-wrapped key at ingest; only the token travels on events.
  • Media: uploads land in a quarantine bucket with no public access. They are scanned, stripped of risky metadata and copied to the clean bucket only after passing. Originals are hashed for chain of custody.
  • Retention: claim-file retention by state and line, enforced with GCS retention policies and Bucket Lock; abandoned drafts purged after a configurable window (e.g. 30 days).
  • Lineage and catalog: Dataplex catalogs every dataset with its classification tags; BigQuery column-level security and policy tags restrict Restricted columns.

Hub-and-spoke on a Shared VPC. No service has a public IP. Public traffic enters only through the global load balancer; private traffic to Google APIs stays inside the VPC Service Controls perimeter; partner and on-prem traffic leaves through fixed, allowlisted paths.

Delivery pipeline

  • Infrastructure as code: Terraform modules (based on Google Cloud Foundation Fabric) per folder and project; state in a locked GCS bucket; plans reviewed in pull requests.
  • CI: Cloud Build (or GitHub Actions with Workload Identity Federation, no keys) runs unit, contract and rules tests, SAST and dependency scans, then builds SBOM-signed images to Artifact Registry.
  • CD: Cloud Deploy promotes dev → stg → prd with Binary Authorization; Cloud Run traffic splitting for canaries; Firebase Hosting preview channels for front ends.
  • Rules and prompts ship through the same pipeline with their own regression suites: golden FNOL transcripts per state with expected checklist output.

09Security, privacy & AI governance

Identity
  • Workforce SSO through IAP and Identity Platform; MFA required
  • Roles as custom claims: agent, supervisor, adjuster, compliance_admin, auditor
  • Firestore Security Rules scope customers to their own drafts
  • One service account per service, no user-managed keys
Protection
  • CMEK with Cloud KMS (HSM) on Firestore, GCS, BigQuery, Cloud SQL
  • Secret Manager for partner credentials, rotated
  • Security Command Center, Cloud Audit Logs (data access on) to a locked sink
  • Mapped to NAIC Insurance Data Security Model Law, NYDFS 23 NYCRR 500, GLBA, CCPA/CPRA, HIPAA where medical data applies

12Decisions recorded

Claims and policy systems: Guidewire and in-house. Both sit behind the claims port, with routing per policy. Guidewire Cloud is reached over HTTPS from fixed NAT addresses; in-house systems over HA VPN.

Contact center: Google Customer Engagement Suite. Agent Assist supplies the live transcript and Conversational Insights keeps call analytics. Both run in the AI project inside the perimeter.

Models: Gemini and Claude side by side on Vertex AI. Each cascade tier has one of each. Evaluation picks the primary per task, and the other provider is the failover.

Launch: personal auto in Wisconsin, Illinois and Michigan. That covers two at-fault states and Michigan no-fault, which drives the most rule variety at launch.

Cloud: the jmarcellis.com organization. Everything lives under one fnol folder with its own guardrail policies and a scoped access policy, so the rest of the organization is untouched.

Still open: rules store. Postgres and CEL as proposed, unless the compliance team already uses a BRMS or DMN tool.
